# Модемные помощники

Эти три ELF-бинарника выполняются **на ZTE MU5250 B31**, а не непосредственно
на macOS. Приложение macOS передаёт их по SSH в свой временный каталог.
Требуются штатные `/lib/ld-musl-aarch64.so.1` и `/usr/lib/libdiag.so.1` модема.
Установки пакетов, QFIL, EDL или прямой записи разделов здесь нет.

Бинарники и исходники не содержат IMEI, резервных NV-записей, EFS-конфига,
паролей или SSH-ключей конкретного устройства. Все тестовые данные синтетические.

## Интерфейсы

`zte_nv --snapshot` читает NV550 обоих индексов и проверяет legacy-алиас
индекса 0. После успешного освобождения DIAG и DeInit выдаёт две строки:

```
APP_NV index=0 data=<256 hex characters>
APP_NV index=1 data=<256 hex characters>
```

Остальные команды принимают абсолютный путь к обычному файлу ровно 512 байт:
`original0[128] + original1[128] + target0[128] + target1[128]`.

| Команда | Назначение |
|---|---|
| `--check-plan-original /path/plan` | Полное сравнение двух записей с исходными |
| `--apply-plan /path/plan` | Запись двух целевых IMEI с проверками и ограниченным откатом |
| `--verify-plan /path/plan` | Полное сравнение двух записей с целевыми |
| `--restore-plan-original /path/plan` | Восстановление исходных из известного исходного/целевого состояния |

Проверяются BCD, Luhn, различие двух целевых IMEI и неизменность 119 байт
после первых 9 в каждой записи. Полный исходный снимок обязателен перед записью;
после каждого индекса проверяются оба полных NV и legacy-алиас. Откат не
перезаписывает неизвестные 128-байтные записи. Повторная операция восстановления
пропускает уже исходные индексы. Обычная запись может повторно записать неизменный
индекс; это совместимо с проверками состояния, но не является оптимизацией числа записей.

`zte_config_read --read-config` выдаёт `EFS_DATA_HEX offset=N length=N data=...`
только после закрытия файла и освобождения DIAG. Завершение обозначается
`EFS_FILE_COMPLETE` и `EFS_RESULT outcome=0`. Поле `crc32` в строке завершения —
обычный CRC32 всего файла; это **не** внутренний MSB-first CRC формата B31.

`zte_config` принимает команду и абсолютный путь к файлу ровно 30146 байт:
`original[15073] + candidate[15073]`.

- `--check-original /path/plan`
- `--check-candidate /path/plan`
- `--enable-flag /path/plan`
- `--restore-original-config /path/plan`

Обе половины проверяются независимо: magic, 249 записей, длина, trailer,
MSB-first CRC32, границы и уникальность ID. ID102 должен быть шестой записью
по смещению 483, с единственным байтом по смещению 499 (0 в original,
1 в candidate). Все остальные байты, кроме CRC по смещениям 12–15, одинаковы.

`/config` открывается только для чтения. Замена выполняется единственным rename
проверенного временного файла после подготовки второй копии для отката.
Временные имена фиксированы и создаются эксклюзивно; чужие или оставшиеся файлы
не удаляются автоматически. Приложение должно сериализовать операции.
Неопределённый результат транспорта прекращает дальнейшие операции с путями и
сохраняет временные файлы для диагностики. Нормальный исходный конфиг принимается
только с проверенными на B31 режимами 0x8d00/0x8d20; временные файлы — строго 0x8d00.

## Сборка и проверка

```
python3 DeviceHelpers/build.py
python3 DeviceHelpers/tests/run_tests.py
```

Для сборки нужен `aarch64-linux-musl-gcc` в PATH либо `ZTE_CROSS_CC`.
Санитайзерные тесты используют host clang и не подключаются к модему.
Итоговые хэши — `bin/manifest.json`; журналы тестов — `tests/.build/*.log`.
Проверены валидаторы планов, HDLC/CRC, ограниченный откат NV, 22 сценария
транзакции EFS и контракт чтения. Эти тесты не заменяют проверку приложения
с реальным модемом; новый общий интерфейс не выполнял живую запись при разработке.
