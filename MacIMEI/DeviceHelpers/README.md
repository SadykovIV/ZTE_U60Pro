# Модемные помощники

## Исследование другой прошивки

`python3 DeviceHelpers/build_support.py` отдельно собирает два временных
инструмента для раздела «Данные для адаптации прошивки»:

- `zte-support-nv --inspect-nv550`: читает только NV550 индексов 0/1 и legacy-алиас;
  возвращает коды DIAG/NV, длины ответов, результат CRC и проверки BCD/Luhn,
  совпадение алиаса. Значения IMEI и 128-байтные записи не выводятся.
- `zte-support-config --inspect-config`: только STAT/OPEN(read-only)/READ/CLOSE
  фиксированного EFS `/config`; возвращает структуру заголовка/записей,
  результат проверки CRC и положение флага 102. Содержимое других полей и
  хэш конфигурации не выводятся. Неизвестная структура остаётся неизвестной.

Это отдельные бинарники с `ZTE_SUPPORT_READONLY`: интерфейсы записи, планов и
экспорта полных данных в них отсутствуют. Рабочие `zte_nv`, `zte_config` и
`zte_config_read` сохраняют прежние команды. Проверка не устанавливает агент,
не включает запись IMEI, не меняет SIM и не перезапускает модем. Для чтения
кратковременно открывается диагностическая сессия MPSS/MODEM; после неё
проверяются освобождение маршрута и DeInit. Это запросы чтения, а не полностью
пассивное наблюдение за файловой системой.

Проверка транспорта может завершиться успешно при неизвестном формате
конфига: пригодность структуры указана отдельно в `SUPPORT_CONFIG_STRUCTURE`.
Сборщик должен сохранять только строки `SUPPORT_*`, `PAIR_*` и `EFS_*`
по точной схеме полей; сторонняя `libdiag` может писать собственный stdout.
Код 20 у NV означает неуспешный снимок: подробная причина находится в
`PAIR_REQUEST` и `PAIR_SNAPSHOT`. Ошибки загрузки библиотеки/символов имеют
отдельные коды 4/5, инициализации — 6, сессии — 7–9.

`python3 DeviceHelpers/tests/run_support_tests.py` выполняет настоящие CLI
с синтетической библиотекой DIAG под ASan/UBSan. Модем не используется.

Эти три ELF-бинарника выполняются **на ZTE MU5250 B31**, а не непосредственно
на macOS. Приложение macOS передаёт их по SSH в свой временный каталог.
Требуются штатные `/lib/ld-musl-aarch64.so.1` и `/usr/lib/libdiag.so.1` модема.
Установки пакетов, QFIL, EDL или прямой записи разделов здесь нет.

Бинарники и исходники не содержат IMEI, резервных NV-записей, EFS-конфига,
паролей или SSH-ключей конкретного устройства. Все тестовые данные синтетические.

## Интерфейсы

`zte_nv --read-imei` используется кнопкой «Прочитать IMEI». Он читает NV550
индексов 0/1 и legacy-алиас. Первичная запись и совпадение legacy обязательны;
если вторичная запись вернула точный статус `NV_NOTACTIVE_S=5`, выводится только
первый IMEI и отдельное состояние неактивной второй записи. Пустой ответ,
ошибка DIAG, иной NV-статус или некорректный IMEI не превращаются в этот случай.
Значения выдаются после подтверждённых освобождения DIAG и DeInit:

```
APP_IMEI index=0 value=<15 digits>
APP_IMEI index=1 value=<15 digits>
```

Для неактивной второй записи последняя строка имеет вид
`APP_IMEI index=1 state=not-active nv_status=5`. Режим не экспортирует полные
NV-записи и не создаёт резервную копию. Требования всех парных операций ниже
остаются прежними; результат чтения не является разрешением на запись.

`zte_nv --snapshot` читает NV550 обоих индексов и проверяет legacy-алиас
индекса 0. После успешного освобождения DIAG и DeInit выдаёт две строки:

```
APP_NV index=0 data=<256 hex characters>
APP_NV index=1 data=<256 hex characters>
```

`--snapshot-available` возвращает полные активные записи и одну строку:
`APP_NV_TOPOLOGY count=1 secondary=not-active-status5` либо
`APP_NV_TOPOLOGY count=2 secondary=active`. Отсутствие NV1 принимается только
после точного статуса NV_NOTACTIVE_S (5), корректного NV0 и совпадения legacy.
Ошибки транспорта и остальные статусы не означают отсутствие записи.

Остальные команды принимают абсолютный путь к обычному файлу ровно 256 байт
(`original0[128] + target0[128]`) для одной записи или 512 байт для пары:
`original0[128] + original1[128] + target0[128] + target1[128]`.

| Команда | Назначение |
|---|---|
| `--check-plan-original /path/plan` | Полное сравнение активных записей с исходными |
| `--apply-plan /path/plan` | Запись активных целевых IMEI с проверками и ограниченным откатом |
| `--verify-plan /path/plan` | Полное сравнение активных записей с целевыми |
| `--restore-plan-original /path/plan` | Восстановление исходных из известного исходного/целевого состояния |

Проверяются BCD, Luhn, различие двух целевых IMEI и неизменность 119 байт
после первых 9 в каждой записи. Полный исходный снимок обязателен перед записью;
после каждого индекса проверяются все активные полные NV, неизменность их числа и legacy-алиас. Откат не
перезаписывает неизвестные 128-байтные записи. Повторная операция восстановления
пропускает уже исходные индексы. Обычная запись может повторно записать неизменный
индекс; это совместимо с проверками состояния, но не является оптимизацией числа записей.

`zte_config_read --read-config` выдаёт `EFS_DATA_HEX offset=N length=N data=...`
только после закрытия файла и освобождения DIAG. Завершение обозначается
`EFS_FILE_COMPLETE` и `EFS_RESULT outcome=0`. Поле `crc32` в строке завершения —
обычный CRC32 всего файла; это **не** внутренний MSB-first CRC формата B31.

`zte_config` принимает команду и абсолютный путь к файлу ровно 30146 байт:
`original[15073] + candidate[15073]`.

- `--check-original /path/plan`
- `--check-candidate /path/plan`
- `--enable-flag /path/plan`
- `--restore-original-config /path/plan`

Обе половины проверяются независимо: magic, 249 записей, длина, trailer,
MSB-first CRC32, границы и уникальность ID. ID102 должен быть шестой записью
по смещению 483, с единственным байтом по смещению 499 (0 в original,
1 в candidate). Все остальные байты, кроме CRC по смещениям 12–15, одинаковы.

`/config` открывается только для чтения. Замена выполняется единственным rename
проверенного временного файла после подготовки второй копии для отката.
Временные имена фиксированы и создаются эксклюзивно; чужие или оставшиеся файлы
не удаляются автоматически. Приложение должно сериализовать операции.
Неопределённый результат транспорта прекращает дальнейшие операции с путями и
сохраняет временные файлы для диагностики. Нормальный исходный конфиг принимается
с проверенными на B31 режимами 0x8d00/0x8d20 (временные файлы 0x8d00)
либо наблюдаемым B04 режимом 0x81a4 (обычный файл 0644). Для B04 оба
временных файла создаются с 0644, и этот режим проверяется до/после commit
и при откате. EFS STAT также возвращает размер, число ссылок и три времени;
uid/gid в этом ABI отсутствуют. Неизвестные режимы не принимаются.

## Сборка и проверка

```
python3 DeviceHelpers/build.py
python3 DeviceHelpers/tests/run_tests.py
```

Для сборки нужен `aarch64-linux-musl-gcc` в PATH либо `ZTE_CROSS_CC`.
Санитайзерные тесты используют host clang и не подключаются к модему.
Итоговые хэши — `bin/manifest.json`; журналы тестов — `tests/.build/*.log`.
Проверены валидаторы планов, HDLC/CRC, ограниченный откат NV, 35 сценариев
транзакции EFS и контракт чтения. Эти тесты не заменяют проверку приложения
с реальным модемом; новый общий интерфейс не выполнял живую запись при разработке.
