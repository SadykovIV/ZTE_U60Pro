# IKEv2: отдельная сеть Wi-Fi, приватные сети через VPN

Выпуск 1.26, контроллер 1.5.0.
Используется штатный strongSwan модема. Наличие `charon`, `swanctl`, плагинов
EAP-MSCHAPv2 и XFRM подтверждено чтением B31 22 октября 2026 года.
Границы изолированной и живой проверки описаны ниже.

## Настройка

В веб-панели агента откройте VPN → IKEv2. Отдельное приложение для настройки
не требуется; те же поля доступны и в клиентах macOS/Windows. Новому профилю
предлагается имя `UserGate`, которое можно изменить.
Введите адрес VPN-сервера, ожидаемое имя сервера в сертификате,
логин, пароль, CA-сертификат PEM и внутренний DNS IPv4. Значение DNS по умолчанию:
`10.0.2.1`. Можно вставить сертификат или выбрать PEM-файл.

Имя сервера проверяется по сертификату; `%any`, маски и отключение проверки
доверия не поддерживаются. Сертификат здесь — доверенный центр сертификации
сервера, а не сертификат клиента: аутентификация клиента — EAP-MSCHAPv2.

Логин и пароль вводятся пользователем в форме, без передачи через чат.
Пароль не возвращается в состоянии/деталях профиля. При редактировании пустое
поле пароля сохраняет прежнее значение. Сохранение профиля само по себе
не изменяет действующее подключение. Для применения нажмите «Подключиться».

Переключатель VPN Wi-Fi управляет и выделенной сетью, и её VPN-подключением.
Выключение останавливает туннель; включение подключает сохранённый выбранный
профиль. Для UserGate подтвердите новый push на телефоне. Повторная команда
включения уже включённой сети не создаёт новую попытку аутентификации.
«Подключиться» также включает выключенную VPN-сеть. После ошибки запуска
сеть остаётся выключенной; прежний профиль восстанавливается без автоматического
подключения к нему. Если VPN Wi-Fi выключен, перезагрузка модема и восстановление
конфигурации не запускают VPN.

При push MFA после обычного подключения на дисплее или в агенте подтвердите
запрос на телефоне. Отдельный код на модеме не вводится. На одну попытку
подключения выполняется один запуск IKE; после истечения ожидания или обрыва
повторите подключение вручную. Периодическая повторная аутентификация отключена,
обновление ключей CHILD_SA сохранено. Конкретный сервер определяет, когда
потребуется новое подтверждение.

## Маршрутизация

| Назначение из VPN Wi-Fi | Путь |
| --- | --- |
| `10.0.0.0/8` | Только IKEv2 |
| `172.16.0.0/12` | Только IKEv2 |
| `192.168.0.0/16` | Только IKEv2 |
| Публичные IPv4 | Напрямую через LTE |
| DNS TCP/UDP 53 | Перенаправление на DNS профиля через IKEv2 |
| IPv6 | Заблокирован в выделенной сети |

Корпоративный сервер должен разрешить требуемые сети в согласованных traffic
selectors. Без соответствующего SA пакеты не передаются через LTE. Публичный
маршрут продолжает работать при недоступном туннеле, но внутренний DNS в этот
момент не отвечает, поэтому новые имена могут не разрешаться. Резервного
публичного DNS нет. DoH/DoT приложений не превращается автоматически в обычный
DNS; для внутренних имён на клиенте должен использоваться DNS этой сети.

Сеть Wi-Fi имеет собственные имя и пароль и использует выбранный профиль.
Основная Wi-Fi сеть не переключается на корпоративный VPN. Одновременно
выбран один профиль для выделенной сети; существующие VLESS/WG/AWG и подписки
остаются в каталоге. Эта функция не добавляет ещё один независимый SSID сверх
уже существующей выделенной VPN-сети.

Подсеть клиентов модема `192.168.50.0/24` занята локально. Совпадение с адресами
корпоративной сети требует изменения адресного плана: IPsec не заменяет
локальную связь клиентов на одном сегменте.

## Реализация

Конфигурация и секреты хранятся в root-каталоге `/data/zte-vpn` с правами 700,
файлы — 600. Пароль нужен strongSwan в восстанавливаемом виде; это не шифрование
от root-доступа к модему. API деталей удаляет пароль; журналы запросов не
сохраняют тела или полные ответы `vpnctl`. Системные `/etc/ipsec.conf`,
`/etc/ipsec.secrets` и доверенные сертификаты не переписываются.

Используются частный VICI socket, XFRM-интерфейс `zvpn-ipsec`, `if_id/reqid`
19090 и таблицы маршрутизации только для входа с `br-vpn`. SNAT к VPN использует
virtual IP из strongSwan, а не второй адрес LTE-интерфейса. Правила ограничены
цепочками ZVPN и собственной таблицей nftables, общая таблица NAT не очищается.

Активация сохраняет предыдущие `config.json` и `active` для отката. Производные
файлы strongSwan создаются из выбранной конфигурации заново. Обновление
контроллера учитывает отсутствие новых IKEv2-скриптов в старой установке и
восстанавливает это отсутствие при откате.

## Приёмочная проверка

После ввода параметров пользователем и подтверждения push нужно проверить
`INSTALLED` CHILD_SA, запрос внутреннего FQDN именно к DNS профиля, затем HTTPS
к возвращённому IP с исходным именем сервера/SNI и проверкой TLS. Проверка с
клиента VPN Wi-Fi подтверждает весь путь; запрос с самого модема по обычной
таблице маршрутизации этого не подтверждает. Дополнительно проверить публичный
IPv4 через LTE и блокировку приватного адреса после отключения туннеля.

Аппаратные результаты и ограничения фиксируются отдельно от локальных тестов.
Личные учётные данные, профили и необработанные журналы в репозиторий не входят.

На B31 22 октября 2026 года выполнены две изолированные проверки в сетевых
пространствах имён: штатный strongSwan 5.9.14 загрузил сгенерированное соединение
с тестовым CA и тестовыми учётными данными без запуска аутентификации; штатные
XFRM, nftables и iptables подтвердили приватные маршруты, LTE-маршрут,
DNS DNAT и SNAT к тестовому virtual IP. После удаления тестового XFRM-интерфейса
приватный маршрут стал недоступен. Эти проверки не заменяют подключение к
UserGate, подтверждение push и проверку корпоративного DNS/HTTPS.

При живой проверке после самостоятельного ввода учётных данных и подтверждения
push пользователем установлен CHILD_SA. Временный DHCP-клиент на `br-vpn`
получил DNS профиля; запрос внутреннего FQDN к этому DNS и HTTPS к полученному
приватному адресу прошли с проверкой TLS (ответ HTTP 302). Маршруты DNS и сайта
использовали `zvpn-ipsec`, публичный IPv4 — `rmnet_data0`. Пользователь подтвердил
появление отдельного SSID на телефоне. Авторизация на самом сайте не проверялась.

Проверка выявила особенность B31: после административного выключения гостевых
портов Wi-Fi перезагрузка настроек с неизменённым UCI не всегда поднимает их.
Guard теперь адресно поднимает включённые гостевые порты после проверок защиты,
DHCP, моста и hostapd; выключенный пользователем диапазон остаётся выключенным.

Технические источники: [XFRM routing](https://docs.strongswan.org/docs/latest/features/routeBasedVpn.html),
[swanctl.conf](https://docs.strongswan.org/docs/latest/swanctl/swanctlConf.html),
[updown](https://docs.strongswan.org/docs/latest/plugins/updown.html).

23 октября 2026 года на B31 проверены выключение VPN вместе с обеими гостевыми
точками, отсутствие самопроизвольного запуска в выключенном состоянии,
включение после подтверждения push и повторное включение без перезапуска charon.
Административно опущенная гостевая точка 2,4 ГГц восстановилась автоматически;
после этого повторно прошли DNS/HTTPS через временного DHCP-клиента на `br-vpn`.
Пользователь подтвердил компактную компоновку и прокрутку на физическом дисплее.
Отдельная изолированная проверка XFRM подтвердила удаление собственных SA/policy
с сохранением состояний с чужими if_id, reqid и mark. Финальный цикл не включал
перезагрузку модема, радиоассоциацию тестового клиента, проверку внешнего
HTTPS через LTE или принудительное восстановление точки 5 ГГц.
