# Подготовка доступа на MU5250/U60 Pro

В **1.24.4 build 45 / Windows 1.24.4.4** подготовка проверяет известные способы
по очереди. Имя прошивки не ограничивает последовательность. Причина отказа
каждого способа остаётся в журнале приложения.

## Последовательность

| Способ | Проверка и действие | Следующий шаг |
| --- | --- | --- |
| Готовый SSH | Проверить доверие к хосту и выбранное устройство | При успехе подготовка завершена без переустановки |
| Работающий USB ADB | Найти USB-устройство, проверить root, идентичность и фактическую среду | При успехе перейти к установке SSH |
| Штатный USB debug через Web | Прочитать `zwrt_bsp.usb`; если `set` доступен, вызвать `set {"mode":"debug"}`. При недоступной introspection допускается одна попытка этого известного метода | Проверить реальный root USB ADB; при отказе перейти к бэкапу |
| Способ через бэкап | Повторно проверить Web identity, запросить и скачать исходный бэкап. Проверить ключ, архив и штатный USB-блок `etc/rc.local` перед правкой | Сохранить оригинал, проверить изменённый архив, загрузить с проверкой SHA-256 и выполнить один restore |
| Установка SSH | Проверить root, Linux ARM64, инструменты, место и целостность установочных файлов | Создать ключи на компьютере, установить агент и SSH, проверить соединение |

Если полученный список методов прямо исключает `set`, программа сразу переходит
к бэкапу. Успех Web RPC, процесс `adbd` и локальный exit code `adb=0` не заменяют
проверку реального root shell. Ошибка локального ADB-инструмента должна быть
устранена: без него результат включения USB ADB невозможно проверить.

Для неизвестной прошивки используется установщик для измеренной совместимой
Linux ARM64-среды. Это позволяет подготовить SSH без совпадения версии с B31/B02.
Требования IMEI, радиоцикла, VPN и Launcher проверяются отдельно; первоначальная
подготовка не подтверждает совместимость всех функций.

## Ключ и загрузочный скрипт

Известный платформенный suffix входит в программу. Полный пароль бэкапа состоит
из IMEI выбранного устройства и suffix. При пустом поле используется известное
значение; непустое поле — точная ручная замена. Неверное введённое значение
не подменяется автоматически. Ручная замена и Web-пароль не сохраняются.

Для восстановления проверяются `Salted__`, расшифровка, gzip/tar, внутренний MD5,
состав и метаданные архива. Поддерживаемый скрипт должен начинаться со штатного
USB-mode блока с двумя чтениями `usb_op` и ветками `codec_id`/`sensor_id`.
Комментарий с путём, похожий текст в строке или дополнительные действия с
`usb_op` не считаются подходящим скриптом. Остальная часть сохраняется побайтно.
Изменённый архив повторно шифруется и проверяется до загрузки.

Программа сначала запрашивает создание бэкапа, затем получает файл. Проверки
подтверждают скачанные байты и выбранное устройство; отдельного подтверждения
времени завершения серверного задания создания бэкапа пока нет.

**«Проверить ключ бэкапа»** выполняет только получение оригинала, проверку ключа
и структуры архива. Для неё нужны адрес и пароль штатного Web; SSH, ADB и пароль
агента не нужны. Результат не включает ADB и не устанавливает компоненты.
Эта проверка независима от распознавания загрузочного скрипта для записи.
[Источники ключа](BACKUP-KEY-RESEARCH.md).

## Продолжение после обрыва

Намерение direct/restore/reboot/install сохраняется до отправки. Продолжение
читает состояние и проверяет результат уже отправленного действия. Restore
и установка не повторяются автоматически. Привязка к выбранному устройству
проверяется при продолжении. Исходные бэкапы остаются в приватном каталоге
пользователя.

Если исходный бэкап уже содержит строку ADB, повторного restore не требуется.
Отдельное первоначальное включение ADB может запросить одну штатную перезагрузку
при отсутствии ADB; после обрыва проверяется результат этой перезагрузки.
Готовые SSH/ADB не требуют повторного ввода ключа бэкапа.

## USB ADB на Windows

`adb devices -l` может показать устройство без поля `usb:`. USB-происхождение
такого кандидата проверяется через `adb -d get-serialno`. TCP ADB, эмуляторы,
неоднозначный выбор и повторяющиеся serial не принимаются за выбранный модем.
Отдельно показываются `offline`, `unauthorized`, ошибка инструмента и отсутствие
устройства. Подсказка о драйвере Windows не подтверждает ошибку драйвера:
пустой список бывает также при неподходящем кабеле или отключённом USB ADB.

## Источники и границы проверки

- [Реализация раннего MU5250](https://github.com/faying/zte-u60-pro-mu5250-manager/blob/main/onboard/install.sh)
  подтверждает `zwrt_bsp.usb.set {"mode":"debug"}` и ожидание ADB.
- [OpenWrt uhttpd `ubus.c`](https://github.com/openwrt/uhttpd/blob/master/ubus.c)
  описывает `method=list`, `params=["zwrt_bsp.usb"]` и объект сигнатур методов.
- [Источник ключа и механизм его получения на устройстве](BACKUP-KEY-RESEARCH.md).

`SET_DEVICE_MODE`, подбор factory-паролей и скрытые factory-методы не входят
в исследованные способы. Полный аппаратный цикл на FLYMODEM B28 и ранних
прошивках пока не проверен. [Локальные проверки и сборки](B31-AUTO-KEY-1.24.4.md).

## Повторная проверка на нашем B31 — 3 октября 2026

Испытание завершено успешно. До него доверенный SSH работал, процесс `adbd`
был запущен, но USB находился в режиме `usb_op=0` и список ADB был пуст.
В реальном `zwrt_bsp.usb` имелся только метод `list`: старый `set` на этой
прошивке отсутствует.

Для проверки загрузочного механизма сохранён исходный `rc.local`, временно
добавлена известная строка `echo 1 > /sys/class/android_usb/android0/usb_op`
и выполнена одна штатная перезагрузка. Реальный код транспорта приложения
обнаружил один USB ADB, дважды проверил root и идентичность, подтвердил
совпадение устройства с доверенным SSH и точные хэши B31/diag-router.

Затем через проверенный ADB восстановлен исходный файл и выполнена вторая
перезагрузка. Подтверждены исходные байты, SHA-256, владелец, группа, права
`775`, время изменения и размер `rc.local`; USB вернулся в режим `0`.
SSH и процесс установленного `/data/zte-agent` работают. Временные файлы
испытания на модеме удалены, приватная локальная копия сохранена.

После переключения USB macOS предпочла его сетевой интерфейс Wi-Fi.
Это не потеря SSH: доверенный SSH оставался доступен по новому маршруту.
Вспомогательный инструмент испытания исправлен для CRLF-ответов ADB и
проверки результата по текущему SSH-маршруту. Защита Wi-Fi перед изменениями
сохранена; реальный откат выполнен через ADB.

Это проверка **загрузочного механизма и транспорта**, а не полный повтор
Web login/upload/restore на заводском модеме. Уже установленный агент не
переустанавливался. Живой проверки ранних прошивок и запуска Windows EXE
в Windows в этой сессии не было.
