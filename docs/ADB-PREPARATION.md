# Подготовка и проверка USB ADB

Инструкция к версии 1.23.3 для Windows и macOS от 3 октября 2026 года.
Подробная пользовательская инструкция также находится под значком информации
рядом с кнопкой предварительной подготовки. Справка переведена на английский.

## Подготовка, рабочее подключение и диагностический ADB

Первоначальная подготовка проходит этапы: **штатный Web → доступ USB ADB
с учётом прошивки → установка агента и SSH → подключение приложения по SSH**.
Если проверенный SSH уже работает, повторная установка компонентов не нужна.
Обычная кнопка «Подключиться к модему» использует SSH; ADB остаётся каналом
подготовки и диагностики, а не признаком готовности всех функций приложения.

Отдельная кнопка **«Принудительно включить ADB»** доступна и для подготовленного
модема с SSH. Нужен пароль штатного Web, но не пароль агента. Операция проверяет
устройство, сохраняет резервную копию и применяет ту же последовательность
методов ADB, что и подготовка. Если root USB ADB уже подтверждён, повторного
переключения не происходит. Агент, ключи и сервер SSH этим действием не
переустанавливаются. На B31 включение через бэкап может перезагрузить модем.
Если проверенный свежий бэкап B31 уже содержит загрузочную строку ADB, но
сам ADB отсутствует, диагностическая кнопка запрашивает одну штатную
перезагрузку для применения существующей настройки. Повторного восстановления
архива в этой ветке нет. Намерение перезагрузки записывается до отправки;
после обрыва связи приложение только проверяет результат.

Диагностическая операция хранится отдельно в `adb-access-pending.json`.
Продолжение проверяет результат уже отправленного запроса, не повторяя его.
Незавершённая первоначальная подготовка и диагностическое включение ADB
не запускаются друг поверх друга. Пока диагностическая операция не завершена,
другие операции изменения модема также не начинаются. Доступность ADB не
отменяет ограничений прошивки для установки компонентов или изменения IMEI.

Изменения и границы проверки: [релиз 1.23.3](RELEASE-1.23.3.md).

## Исправленная причина ложного отсутствия ADB

В Windows `adb devices -l` может показать готовое устройство без поля `usb:`.
Предыдущий основной транспорт отбрасывал такую строку. Теперь USB-происхождение
подтверждается через `adb -d get-serialno`; результат должен совпасть с кандидатом.
TCP ADB и эмуляторы не принимаются за USB. Дублирующиеся serial и неоднозначный
результат останавливают выбор. Этот разбор используется при подготовке,
подключении и диагностике.

Отдельно показываются `offline`, `unauthorized`, отсутствие прав, ошибка
локального инструмента и отсутствие устройства. Подсказка о Windows-драйвере
не является результатом проверки драйвера: пустой список ADB также бывает при
неподходящем кабеле, отключённой USB-композиции или неподключённом модеме.

## Последовательность

| Ситуация | Действия | Подтверждение результата |
|---|---|---|
| SSH/агент уже настроены | Проверка доверия, устройства и готовности существующей установки | Подготовка завершается без повторного включения ADB |
| USB ADB уже работает | Выбор USB, root, ARM64, Web identity, CID и хэши | Переход к проверке совместимости установщика |
| Штатный USB debug объявлен | JSON-RPC `list` для `zwrt_bsp.usb`; один `set {"mode":"debug"}` | До 90 секунд ожидания реального root ADB |
| Introspection недоступна, известная CN MU5250 ≤ B27 | Один исторически подтверждённый `set {"mode":"debug"}` | Такая же проверка ADB; отсутствие метода в полученном списке запрещает эту попытку |
| ADB не появился, точная B31 | Свежий проверенный бэкап, ADB-строка в `etc/rc.local`, upload с проверкой SHA-256, один restore | Перезагрузка и ожидание root USB ADB до 4 минут |
| ADB-строка уже есть | В обычной подготовке — проверка доступности; в принудительном диагностическом режиме B31 — одна штатная перезагрузка при отсутствии ADB | Повторного восстановления нет |
| Запрос direct/restore/install уже отправлен | Продолжение по журналу, чтение состояния | Запросы автоматически не повторяются |
| Неизвестная прошивка | Диагностика доступности; ограничения установщика сохраняются | Наличие ADB не объявляет прошивку совместимой с установкой или IMEI |

Локальная ошибка запуска/разбора ADB до первой попытки включения останавливает
изменения на модеме. Во время ожидания после отправленного запроса временные
ошибки чтения повторяются в пределах ожидания и остаются в диагностике.

Для первоначальной подготовки сохраняется зашифрованный исходный бэкап.
Расшифровка и Backup-key suffix нужны только в ветке B31 restore. После
неудачного direct-включения перед fallback требуется повторный вход в Web,
совпадение идентичности и новый бэкап. Неподтверждённый Web не допускает restore.

Успех RPC, работающий процесс `adbd` и локальный exit code `adb=0` не означают
готовый root shell. Удалённый код команды проверяется отдельным маркером.
Поддержка установщика остаётся ограничена точными B31/B02 профилями; галочка
общей проверки прошивки не снимает эти ограничения.

## Источники и границы доказательств

- [MU5250-OpenUI: deployment](https://github.com/dklasens/MU5250-OpenUI/blob/main/docs/DEPLOYMENT.md)
  описывает границу старого USB debug и backup/restore. Утверждение этой страницы,
  что современный `setup.sh` всё ещё выполняет direct-вызов, не соответствует
  проверенному текущему скрипту; в нём только SSH → имеющийся ADB → unlock.
- [Реализация раннего MU5250](https://github.com/faying/zte-u60-pro-mu5250-manager/blob/main/onboard/install.sh)
  подтверждает `zwrt_bsp.usb.set {"mode":"debug"}` и ожидание ADB. Живой проверки
  на ранней прошивке в этой сессии нет.
- [OpenWrt uhttpd `ubus.c`](https://github.com/openwrt/uhttpd/blob/master/ubus.c):
  `method=list`, `params=["zwrt_bsp.usb"]`, результат — объект сигнатур методов.
  Session ID не является элементом массива имён объектов.
- Исторические журналы реального B31 и резервные копии содержат данные устройства
  и не входят в публичный репозиторий.

`SET_DEVICE_MODE`, `adb_switch` с подбором пароля, `fac_open` и скрытые
factory-методы не входят в автоматическую последовательность. Подтверждения
`SET_DEVICE_MODE` для MU5250 в исследованных источниках нет.

## Публичная сборка

[Сборка и локальные проверки](BUILD.md) не требуют подключённого модема.
Встроенного backup-key suffix и доверия к чужому устройству в приложении нет.
Работающий ADB, штатный direct-метод и продолжение проверки после отправленного
restore/reboot не требуют повторного ввода suffix.

## Повторная проверка на нашем B31 — 3 октября 2026

Испытание завершено успешно. До него доверенный SSH работал, процесс `adbd`
был запущен, но USB находился в режиме `usb_op=0` и список ADB был пуст.
В реальном `zwrt_bsp.usb` имелся только метод `list`: старый `set` на этой
прошивке отсутствует.

Для проверки загрузочного механизма сохранён исходный `rc.local`, временно
добавлена известная строка `echo 1 > /sys/class/android_usb/android0/usb_op`
и выполнена одна штатная перезагрузка. Реальный код транспорта приложения
обнаружил один USB ADB, дважды проверил root и идентичность, подтвердил
совпадение устройства с доверенным SSH и точные хэши B31/diag-router.

Затем через проверенный ADB восстановлен исходный файл и выполнена вторая
перезагрузка. Подтверждены исходные байты, SHA-256, владелец, группа, права
`775`, время изменения и размер `rc.local`; USB вернулся в режим `0`.
SSH и процесс установленного `/data/zte-agent` работают. Временные файлы
испытания на модеме удалены, приватная локальная копия сохранена.

После переключения USB macOS предпочла его сетевой интерфейс Wi-Fi.
Это не потеря SSH: доверенный SSH оставался доступен по новому маршруту.
Вспомогательный инструмент испытания исправлен для CRLF-ответов ADB и
проверки результата по текущему SSH-маршруту. Защита Wi-Fi перед изменениями
сохранена; реальный откат выполнен через ADB.

Это проверка **загрузочного механизма и транспорта**, а не полный повтор
Web login/upload/restore на заводском модеме. Уже установленный агент не
переустанавливался. Живой проверки ранних прошивок и запуска Windows EXE
в Windows в этой сессии не было.
